## Notes & Intelligence

- **2026-10-22 — AWS bulletins 2026-142/143-AWS published (live-verified against aws.amazon.com/security/security-bulletins 2026-10-22 ~07:45 UTC; lowercase slug URLs `…/security-bulletins/2026-1NN-aws/`):**
  - **2026-142-AWS — CVE-2026-112408 (Amazon SageMaker Python SDK V2 < 2.257.3, V3 >= 3.0.0 < 3.10.0; GHSA-5rx8-8fr2-f855 per bulletin; publication date 10/21/2026 12:30 PM PDT):** the SDK's `default_bucket()` uses a **predictably named S3 bucket and never verifies the caller's AWS account owns it** — a remote actor who **creates that bucket name first** (bucket-squatting) achieves **code execution in the victim's remote SageMaker execution environment and obtains its IAM credentials**. Fix: 2.257.3 / 3.10.0; workaround: set an explicit `default_bucket` on `sagemaker.Session` or SDK config instead of the auto-generated name. Credited to Dan Gansel (Upwind Security) via coordinated disclosure. **Hunting read: classic cloud resource-name-preemption class (same family as S3 bucket squatting / subdomain takeover) now confirmed inside an ML-SDK default — any SDK/CLI that auto-derives storage resource names without ownership verification is a squat-to-RCE lane; the durable probe battery: (1) is the resource name predictable from account-external inputs, (2) does the consumer verify ownership before trusting content, (3) what runtime privileges does the trust boundary carry (here: SageMaker execution-role IAM creds). Directly VRP-relevant (AWS-distributed SDK) — and portable: hunt predictable-bucket/container/registry names in every program with SDK-generated infrastructure. No global GHSA mirror was visible via advisory API at sweep-47 check time — bulletin remains authoritative.** Source: https://aws.amazon.com/security/security-bulletins/2026-142-aws/
  - **2026-143-AWS — CVE-2026-109618 & CVE-2026-109619 (PHP web runtimes, CRITICAL):** two **unauthenticated remote-code-execution** issues in PHP reachable by crafted web requests against PHP workers (code execution, process-data read, or DoS; bounded to the affected worker, no established cross-customer propagation). Affected: PHP 8.5.0–8.5.11 (fix 8.5.12), 8.4.0–8.4.26 (fix 8.4.27), 8.3.0–8.3.35 (fix 8.3.36), 8.2.0–8.2.34 (fix 8.2.35); **PHP 5.4–8.1 EOL with NO upstream fix planned — migration only.** AWS states **AWS services themselves are not impacted**; customer-facing surfaces with mitigation status: WorkMail (config controls applied, PHP 8.3.36 upgrade targeted 2026-10-22), Elastic Beanstalk PHP platform v4.13.12 released 2026-10-21 (follow-on with upstream fix targeted 10-22), Amazon Linux updated PHP packages (non-commercial regions 10-22), Lightsail updated blueprints. AWS WAF compensating controls published for interim. **Hunting read: this is the ecosystem story, not a VRP report vector (AWS says services not impacted) — but two internet-facing unauth PHP RCEs with EOL branches left unfixed is a fingerprinting goldmine: any in-scope target banner-fingerprinted on PHP ≤ 8.1, or 8.x below the fixed points, is sitting on a known unauth RCE while the disclosure goes public — expect mass scanning within days and adjust passive-recon watchlists accordingly; for report-quality evidence on owned labs, this is a rare legal validation surface for PHP request-handling sinks.** Sources: https://aws.amazon.com/security/security-bulletins/2026-143-aws/

- **2026-10-20 — AWS bulletins 2026-140/141-AWS published (live-verified against aws.amazon.com/security/security-bulletins 2026-10-20 ~20:45 UTC; lowercase slug URLs `…/security-bulletins/2026-1NN-aws/`; no GHSA mirrors found via advisory API for either CVE at check time):**
  - **2026-140-AWS — CVE-2026-112380 (Kiro Crew < 0.7.2):** authorization issue in the **WhatsApp channel + internal subagent run-control endpoints** of Kiro Crew, AWS's open-source personal AI agent that runs tools on the operator's machine. Where an operator had added a WhatsApp group to `whatsapp.groups` (or set `whatsapp.dm_policy` to open), **any member of that group could send instructions to *another session's* subagent**, which then executed them on the operator's machine under that session's approval policy — **with the audit trail attributed to the operator, not the actual sender**. Default config is NOT affected (`whatsapp.groups` empty, `dm_policy=self`, unlisted groups dropped pre-dispatch). Fix in 0.7.2 (PR #14338): group traffic now subject to the same per-user allowlist as DMs (deny-by-default), untrusted turns run on a dedicated tool-less agent, and every subagent run-control route requires verified caller identity + ownership check. Mitigation without upgrade: empty `whatsapp.groups` / keep `dm_policy=self`, or disable the WhatsApp channel. Hunting read: **cross-session subagent instruction injection with operator-attribution laundering** — the fifth confirmation of the AI-agent attribution-confusion class (GitLab CVE-2026-96893 sibling) and the first on an AWS-distributed agent framework; the durable probe battery for any messaging-channel agent bridge: (1) does channel traffic cross session boundaries, (2) is sender identity verified per run-control route or only at channel attach, (3) whose identity does execution get logged under. Channel-allowlist config = privilege boundary — test deny-vs-allow dispatch order. Directly VRP-relevant (AWS-distributed software). Source: https://aws.amazon.com/security/security-bulletins/2026-140-aws/
  - **2026-141-AWS — CVE-2026-112407 (AWS CICD-toolchain-for-serverless-applications < 1.0.11):** incorrect privilege assignment in the toolchain's **IAM policy** lets a remote authenticated user **with push access to the application source repository** escalate privileges and access/modify resources **outside the application stack in the same AWS account** via application templates deployed by the pipeline. Fixed in 1.0.11; AWS recommends upgrading existing stacks and patching forks. Credited to an external researcher (Changli, Xidian University) via coordinated disclosure. Hunting read: continues the standing **deploy-pipeline IAM-overgrant lane** (same meta-class as GitLab CVE-2026-16301 downstream-pipeline execution and the GitLab CI protected-variable family): repo-push is a much lower trust level than what a pipeline's role can reach — for any IaC/CI template that provisions its own pipeline roles, diff the pipeline role's policy against the minimum the declared app needs, and test whether template content is a caller-controlled input to the IAM policy generator. Sample-app-grade bugs matter: the same pattern ships in customer-built toolchains. Source: https://aws.amazon.com/security/security-bulletins/2026-141-aws/

- **2026-10-20 — Apache Airflow *Amazon provider* AWS auth manager SAML login-CSRF, GHSA-2738-4g2m-64cv / CVE-2026-86467 (apache-airflow-providers-amazon < 9.38.0):** the SAML login handler discards the `AuthnRequest` ID and the callback validates assertions without requiring a matching `InResponseTo` → an unauthenticated attacker who lures a victim to an attacker page can complete a SAML login **in the victim's browser using the attacker's own assertion**, silently landing the victim in an Airflow session the attacker controls (subsequent victim work lands in the attacker's session). No victim Airflow credential needed. Fix: providers-amazon 9.38.0. Published 2026-10-20T03:32Z, **unreviewed tier — no CVSS assigned; confirm against the Apache list thread before relying on severity** (refs: apache/airflow PR 73698, lists.apache.org thread). Note: Apache project, not AWS-distributed software — VRP relevance is via the AWS auth-manager integration surface, not a direct AWS report vector. Hunting read: **missing InResponseTo binding is now a confirmed repeat class** — same login-CSRF fixed in the Keycloak auth manager as CVE-2026-40948 is explicitly cited; every SAML SP that skips assertion→request binding is probeable via victim-lure. Standing checklist addition: for any SSO/SAML integration, test whether the callback rejects assertions whose InResponseTo is absent or foreign.

- **2026-10-19 — AWS bulletins 2026-131/132-AWS folded in (live-verified against aws.amazon.com/security/security-bulletins 2026-10-19 ~23:45 UTC; bulletin pages do not expose publish dates in static HTML, so treat as recent, published before the 133–139 batch of 10-17/18):**
  - **2026-131-AWS — CVE-2026-107608 (aws-cdk-lib < 2.267.0, GHSA-h6j4-qpp7-q28p per bulletin references, no global GHSA mirror found via API 10-19):** when CDK asset bundling is invoked with a Dockerfile, the Docker build can insert a symlinked file/directory into the bundling *output* without that symlink ever being an input to the bundling process → unintended files smuggled into deployed CloudFormation asset artifacts. Fix: aws-cdk-lib 2.267.0; workaround: audit that no untrusted code executes inside the bundling container. Hunting read: build-output canonicalization — a trusted pipeline stage (asset bundling) trusts its container's filesystem output, so the container becomes the smuggling channel; same trust-boundary meta-class as the Amplify generated-resolver entry (trust what the generator emits, not the declared intent).
  - **2026-132-AWS — CVE-2026-107783 (AWS Tools for PowerShell ≤ 5.0.305, fixed 5.0.306, GHSA-q3x5-q6rm-c7p3 per bulletin references, no global GHSA mirror found via API 10-19):** an IAM user's **cleartext Management Console password** can be recovered from command output and log artifacts (notably when `-WhatIf`/`-Confirm` is used with cmdlets carrying sensitive arguments). Local-user recovery, but the leaked secret is a *console credential*, not a token. Hunting read: same lineage as the SageMaker SDK stderr→CloudWatch leak (2026-134) — the SDK tooling layer echoes full argument vectors into logs/what-if previews; any cmdlet/CLI wrapper that prints "what it *would have* run" with embedded credentials is a standing probe class across SDK tooling in VRP scope.
  - Batch meta-note: both are dev-tooling-layer bugs (CDK bundler, PowerShell tools), not service-plane — AWS keeps crediting toolchain supply-chain issues steadily; watch the SDK/CLI/ IaC lane in addition to service endpoints.

- **2026-10-19 — vmgenid driver NULL-deref on Firecracker snapshot-restore path, GHSA-p8pc-3hw3-fwp9 / CVE-2026-98841:** Linux kernel `virt: vmgenid` driver: both probe paths register the generation-changed notification handler *before* assigning `driver_data`, which the handler dereferences. The advisory explicitly names **Firecracker snapshot restore** as the trigger — the VMM can inject the generation-changed notification while restoring a guest whose snapshot predates driver probe, so the IRQ fires with `driver_data` still NULL → kernel panic (NULL deref @ offset 0x10). The IRQ is also `IRQF_SHARED`, so a line-sharing device can trigger the handler just as early. Fix: set `driver_data` before registering handlers (kernel stable commit linked in the advisory). Published 2026-10-18T18:32Z, unreviewed-tier kernel-bot GHSA mirror — **no CVSS/GHSA severity assigned; no AWS bulletin yet** (live-verified against the GitHub advisory API 2026-10-19). Hunting read: rare advisory that names a VMM behavior as the trigger — the *snapshot/restore lifecycle* of microVMs is a fresh race window for guest-kernel init bugs; if probing Firecracker-adjacent VRP surfaces (snapshot/restore features, warm-start), guest-boot-ordering bugs triggered by VMM-injected events are a live class. Local/guest-side DoS primitive (panic at probe), so posture intel, similar to the nitro_enclaves entry below.
- **2026-10-18 (later same day) — Nitro Enclaves kernel-driver use-after-free, GHSA-8pj3-87fr-9h94 / CVE-2026-98775:** Linux kernel `nitro_enclaves` driver error path: when `SLOT_ALLOC` fails after `anon_inode_getfile()` succeeded in `ne_create_vm_ioctl()`, the cleanup calls `fput(enclave_file)` then frees `ne_enclave`; `ne_enclave_release()` later dereferences `ne_enclave->slot_uid` on the freed object → KASAN slab-use-after-free reachable by any local user with access to the enclave device node. Fix: clear `enclave_file->private_data` before `fput()` (kernel stable commits linked in the advisory). Published 2026-10-18T18:32Z via the unreviewed tier — kernel-bot GHSA mirror, **no CVSS/GHSA severity assigned; no AWS bulletin yet** — confirm against NVD/kernel stable before relying on impact claims. Hunting read: extends the same-day virtio-net guest→host lane to the *enclave* boundary, and the bug class is generic error-path ownership (cleanup order between file-release and struct-free) — probe any ioctl that installs a file descriptor before fully validating allocation. Local-primitive only (needs `/dev/nitro_enclaves` access on an instance the customer controls), so VRP relevance is posture intel rather than a direct report vector.
- **2026-10-18 — AWS bulletins 2026-137/138/139-AWS published overnight (live-verified against aws.amazon.com/security/security-bulletins 2026-10-18; bulletin URLs use lowercase slug form `…/security-bulletins/2026-1NN-aws/`):**
  - **2026-137-AWS — CVE-2026-99999 (Linux kernel virtio-net/TAP):** privileged guest-VM actor sends crafted packets → host kernel memory corruption on KVM-based hypervisors running unpatched kernels 4.4–6.18 → host memory disclosure or DoS. **AWS-managed compute (EC2, Lambda, Fargate) explicitly NOT affected** — exposure is self-managed VM hosts, including Firecracker-based VMMs; fixed via Amazon Linux kernel updates (AL2/AL2023, kernel 6.18.51+ etc.). Credited to Paulos Yibelo (pwn.ai). Hunting read: guest→host boundary via the *networking virtio path* — for any sandbox/microVM product in VRP scope (Lambda-style isolation, Fargate, third-party Firecracker deployments), the packet-shaped-input-to-host-kernel class is a fresh cross-boundary template; also note AWS's public "not affected" attestation pattern for managed services — useful framing for report impact statements.
  - **2026-138-AWS — CVE-2026-109587 / CVE-2026-109588 (FreeRTOS-Kernel Arm Cortex-R82 MPU port):** unprivileged task escapes its MPU region on buffer args to MPU system calls (authorization gap), plus a length-truncation in stream-buffer buffer validation → unprivileged read/write of privileged kernel memory. Affects V11.3.0/V11.3.1 with `configENABLE_MPU=1`; fixed V11.3.2. GHSA mirrors: GHSA-pv9j-rq42-3fjc, GHSA-qf4j-6f5j-876g. Credited to Ada Logics + Anthropic. Hunting read: the MPU *system-call buffer authorization check itself* is the vulnerable component — sandbox-enforcement code is attack surface, same meta-lesson as the GitLab regex-compiler wave.
  - **2026-139-AWS — CVE-2026-102551 / CVE-2026-102552 (FreeRTOS-Plus-TCP ≤ V4.4.1, fixed V4.4.2):** IPv6 Router Advertisement handler doesn't verify the RA is on-link → remote third-party can steer the device's IPv6 gateway/prefix/address → traffic interception (reachable in *default config* with IPv6+RA enabled). DNS resolver accepts replies without validating source == queried server → DNS cache poisoning. **Notable: the DNS fix is opt-in (`ipconfigDNS_CHECK_REPLY_SOURCE_IP`, disabled by default) — upgrading alone does NOT remediate**, a rare "patched but still vulnerable by default" case worth quoting in IoT/OT-adjacent reports. GHSA mirrors: GHSA-pjq5-fqrr-g6pv, GHSA-h4fw-pv82-p7h5. Credited to Cipher / Causal Security. Hunting read: source-verification-of-unsolicited-replies (RA, DNS, any request/response pair lacking tokens) is the class — off-path injection into stateless protocol handlers.
  - Cumulative hunting-read for the batch: three of three bulletins this week are **boundary-validation failures in enforcement/trust code** (hypervisor network path, MPU syscall guard, protocol source checks) rather than feature bugs — continues the same meta-pattern as the GitLab regex-compiler and Amazon Amplify generated-resolver entries.

- **2026-10-14/15 — AWS bulletins 2026-133/134/135-AWS: three advisory classes folded into the standing hunt lanes (live-verified against aws.amazon.com/security/security-bulletins 2026-10-18):**
  - **2026-133-AWS — CVE-2026-108096 (Amplify API Category):** improper authorization in query resolvers *generated* by `@aws-amplify/graphql-index-transformer` — an authenticated user can read records owned by other users of the same app via crafted queries on AppSync APIs built from declared auth rules. Hunting read: when authorization is *code-generated* from a declarative schema, the generated resolver is the enforcement point — authz-rule → resolver compilation gaps are a systematic probe class for any schema-to-API generator, not just Amplify.
  - **2026-134-AWS — CVE-2026-110248 (SageMaker Python SDK):** on failed Git clone, repo credentials in subprocess *error output* are written unredacted to CloudWatch Logs; log readers get plaintext creds. Hunting read: the error path is the leak path — subprocess/CLI wrapper stderr is a standing credential-disclosure probe wherever tools echo commands with embedded auth into logs.
  - **2026-135-AWS — CVE-2026-110310 (S3 Encryption Client for .NET):** a remote user able to read encrypted objects can downgrade the padding scheme recorded in object *metadata* to legacy RSA PKCS#1 v1.5, then exploit the resulting Bleichenbacher padding oracle to recover the wrapped envelope key and decrypt. Hunting read: metadata-trusted crypto negotiation (client reads attacker-influenced algorithm fields) is the root class — cross-boundary impact from an object-read-only principal to plaintext recovery.
  - All three extend the managed-service authz/crypto-boundary lineage above (Q Business user-controlled key, Neptune Gremlin). No GHSA mirrors found in the GitHub advisory API for these CVEs as of 2026-10-18 — AWS bulletins are the authoritative source.

Hunting-read value: import/parse paths on customer-supplied graph data are a live RCE + credential-theft surface even behind standard auth.
